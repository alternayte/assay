# Design pages

## What it does
Assay indexes the source code of repository connections and writes a design page for each repository, system and multi-repository service.
A design page says what the code does, how it works and why, in ASD-STE100 prose with Mermaid diagrams.
Each sentence, diagram node and diagram edge cites a code passage, a knowledge passage or a claim.
People correct a page section by section, and their edits stay until a reviewer accepts a change.
Pages update after each sync, and readers see only content from their visible set.

## Decisions
- Source files are items. Each top-level declaration is one passage with a line range — citations and staleness reuse passage hashes.
- tree-sitter grammars parse Go, TypeScript/JavaScript, C# and Python through github.com/odvcencio/gotreesitter, a pure-Go runtime (MIT). Other files split at blank lines — pure Go keeps CGO_ENABLED=0 and the single static binary, with no WASM build step.
- The connectors setting adds maxCodeFilesPerRepo (10000) and maxCodeFileKB (256). The sync counts knowledge files first, against their own limits — code must not push out READMEs and ADRs.
- The sync skips vendor/, node_modules/, dist/, bin/, obj/, *.min.js and files with a "Code generated" or "<auto-generated>" header, with the reason generated. The skip list is a UI setting — generated code adds cost and no design.
- Each connection has code globs with a default per language. Empty globs turn code indexing off — the owner controls the cost.
- The repository entity page gets a Design tab: overview, architecture diagram, one section per component, data — one page per repository is the unit that people read.
- Components come from Go package directories under cmd/ and internal/, .csproj files, workspace package.json files and Python packages. Small components merge into their parent until 12 sections or less remain. Components are not entities — thousands of entities add resolution and review load for little value.
- A system entity, and a service entity with two or more implementing repositories, gets a Design tab with a service diagram and one section per repository — products span many repositories.
- implements and part_of claims group repositories. Code extraction proposes depends_on, provides_api and consumes_api claims with code evidence — grouping keeps sources, visibility and corrections.
- The decision kind repo_system groups a repository that has no implements or part_of claim. Inputs: README, description, CODEOWNERS team, name prefix, code edges, linked Jira and ADO projects, and up to 5 candidates plus new and none — most repositories have no catalog-info.yaml.
- repo_system new proposes a system registry record. none leaves the repository alone. Catalog and human registry claims outrank repo_system through source priority — people stay in control.
- The lint requires each sentence to cite a passage or claim from the input. A why sentence cites a knowledge passage or a human edit, or the page says that the reason is not recorded — the model must not invent intent.
- The generator drops a diagram node or edge without a source — diagrams follow the same rule as prose.
- Each section is a versioned record with a model or user author. Report a problem gives a card. Edit follows REQ-REG-003. The lint warns on human text and does not block it — corrections reuse the review flow.
- A human version is pinned. When its cited passages go stale, the model drafts an update as a diff card. An unpinned model section regenerates when stale — human corrections never disappear.
- A River job runs after each sync with code globs. It builds component digests, then sections, then the overview and diagrams. Each step reads the digests, not the code — the cost scales with the change, not the repository.
- A component digest stores the hash of the sorted passage hashes of its component. Each sync finds the components again — added code and new components update the page, not only cited code.
- The design model function on the Models page holds the endpoint, the model and the monthly budget. The design setting holds a token budget per repository and run, the section limit and the words per section. A run that reaches the budget keeps its done sections, marks the rest stale and logs the reason — cost has a hard stop.
- The page shows the last good version with an Updating mark during a run. Reviewers can regenerate by hand — readers never see an empty page.
- System design pages cache per visibility key — a hidden repository never appears in a node, edge or sentence.
- Search and ask include code passages, cited with the file and line range. "Open in source" opens the blob at its commit. The search Code filter is off by default — prose results stay first.
- MCP gets get_design_page. REST gets GET /api/v1/entities/{key}/design.md with footnote citations — agents use design pages to learn a codebase.
- Mermaid (MIT) renders diagrams in the web app, and section edit shows a live preview — diagrams are source text that people can correct.
- v1.1.0 also fixes the open follow-ups F-R1-02 to F-R1-15 and F-R2-01 to F-R2-02 in .build/decisions.md. Each fix has a regression test — visibility leaks and data loss block a release.

## Out
- Documentation for each function or class.
- Export of AGENTS.md as a pull request.
- Branches other than the default branch.
- Webhooks. Pages update only on the sync schedule.

## How I know it works
- `sh scripts/install.sh --demo` syncs the Acme code repositories in the GitHub and ADO fixtures. Each repository shows a Design tab with an overview, an architecture diagram and component sections.
- Each sentence on a design page has a citation chip. The chip opens the code passage with its line range.
- An Acme repository without catalog-info.yaml shows a repo_system card. Accept puts the repository on its system design page.
- A member without the acme-restricted connection opens a system design page and sees no restricted repository, node or sentence.
- A fixture commit changes one function. After the next sync, only the section that cites it regenerates. A fixture commit adds a package, and a new section appears.
- A reviewer edits a section. A later sync that changes its cited code gives a diff card and leaves the edit in place.
- A low token budget stops the run, and the run log shows the reason.
- `curl $ASSAY/api/v1/entities/{key}/design.md` returns Markdown with footnotes. The MCP get_design_page tool returns the same page.
- `assay eval` shows repo_system precision and recall per band.
- `assay reindex` runs, and each follow-up has a passing regression test in `just ci`.
